# Employee Domain

Status: **Implemented (Phase 04)**. See [ADR-020](../adr/ADR-020-employee-identity-model.md) (identity model), [ADR-021](../adr/ADR-021-employee-number-generation.md) (employee number), [ADR-022](../adr/ADR-022-position-manager-assignment-history.md) (assignment history), [ADR-023](../adr/ADR-023-employee-lifecycle-and-status.md) (lifecycle), [employee-architecture.md](../architecture/employee-architecture.md) for the technical layering.

## The shape

```
Employee (identity core: employee_number, name, DOB, gender, nationality, marital_status, profile_photo)
  ├── EmployeeContact (1:1 — emails, phones, address)
  ├── EmployeeEmployment (1:1 — joining_date, employment_type, status, probation/confirmation/termination)
  ├── EmergencyContact (1:many — no OneToOne, an employee may list several)
  ├── EmployeePositionAssignment (1:many, historical — who has occupied which Position, and when)
  └── EmployeeManagerAssignment (1:many, historical — who has reported to whom, and when)
```

`Employee.current_position` and `Employee.current_manager` are denormalized pointers, synchronized only by the assignment services, never the source of truth — see ADR-022.

## Employee ≠ Position ≠ Job ≠ User

```
Job          — the role ("Restaurant Manager"), Phase 03
Position     — a specific seat ("RM-LHR-001"), Phase 03
Employee     — a person ("Ahmed Khan"), Phase 04
User         — a login identity, optional, Phase 01
```

`Employee.user` is a nullable `OneToOneField` — most employees (restaurant crew) will never have one. Linking/unlinking is an explicit action (`EmployeeUserLinkService`), never automatic (Phase 04 brief §49-§51).

## Employee number

`EMP-000001` style, generated by `EmployeeNumberService` from a concurrency-safe counter row — never derived from the database primary key. See ADR-021.

## Employment status vs. `Employee.is_active`

There is exactly one status field, `EmployeeEmployment.status`. `Employee.is_active` is a computed property reading it — there is no second, independently-editable boolean that could contradict it. See ADR-023.

## What's deliberately NOT here yet

- **No `Person` layer** — `Employee` carries identity directly. Rehire (a person leaving and later returning) is not modeled as a distinct scenario; a rehire today gets a brand-new `Employee` row with no link to their prior one. See ADR-020 for the exact, additive migration path if this becomes a real requirement.
- **No employee documents** (CNIC, contracts, certificates) — explicitly deferred (Phase 04 brief §44); the architecture doesn't block a future `EmployeeDocument` model FK'ing to `Employee`.
- **No bulk import/Excel upload** — deferred (§73); `EmployeeService.create_employee` is already the single write path a future importer would call per row.
- **No multi-address support** — `EmployeeContact` has one embedded address (current), not a separate `EmployeeAddress` table with types (Current/Permanent/Other). Same deliberate simplification Phase 03 made for `Location.address`.
- **No `PositionHistory`/`EmploymentHistory` audit table** — history lives in the assignment tables themselves (which ARE the history) plus the existing `apps.audit` log for status-transition events. No duplicate temporal table.

## Authorization

Every list/detail read routes through `apps.employees.permissions`, which reuses `apps.organization.permissions.restrict_by_organization` directly — `Employee` has no `organization_unit`/`location` field of its own, so scoping traverses through `current_position__organization_unit`/`current_position__department__...` field paths. Object-level access (Detail/Update/History) additionally always includes the viewer's own linked record, so "My Profile" (`MyProfileView`) works for a user with zero organization scope. See [employee-architecture.md](../architecture/employee-architecture.md#authorization).

## Seed data

`python manage.py seed_employees` — idempotent, builds on `seed_organization` (Phase 03): hires a realistic Restaurant Manager → Assistant Manager → Shift Leaders → Crew reporting chain into each seeded restaurant's positions, plus one HR Officer at corporate. Fictional names only.
